# アーキテクチャ

## Phase 1 の責務

| 部品 | 役割 | 実行のタイミング |
| --- | --- | --- |
| プラグインエントリ | 定数・オートロード・ライフサイクル登録 | WordPressによる読込 |
| 管理画面 | 診断・設定・実装状態・ログ出力 | 権限を持つ管理者の操作 |
| 環境収集 | PHP設定とWordPress設定の安全な型への変換 | 管理画面で診断するとき |
| 純粋な診断器 | 環境値から日本語の診断行を生成 | 明示的な診断処理 |
| Logger | 許可されたイベントとメタデータのJSONL書込 | イベント発生時 |
| Redactor | 秘密情報・自由入力の排除 | 書込時とエクスポート時 |
| Exporter | 時間範囲を絞ったZIPを作成 | nonce検証済みの管理者操作 |
| CIと配布スクリプト | テスト、解析、依存監査、ZIP作成 | 開発・プルリクエスト |

診断は設定とファイル権限の読み取りが中心です。全ファイル走査、外部脆弱性DB照会、WordPressコアのチェックサム検証はPhase 1では行いません。通常のフロントエンド要求で重い診断を実行しない構成にします。

ログは機能ごとに分離し、外部サービス用クライアントへ秘密値を渡す将来の実装でも、ログへは固定イベントコードと限定的な数値結果だけを渡します。エラーメッセージ全文や例外オブジェクトをシリアライズしません。

## 信頼境界

WordPress管理者の権限とnonceを管理操作の入口で検証します。ブラウザーから渡る値、ログファイルの既存行、外部APIの返却値、配布メタデータはすべて未検証の入力として扱います。OSユーザーやWebサーバー設定が侵害された場合まで、プラグインのファイル権限だけで保証するものではありません。

ログ保存先は公開領域の外に置きます。プラグイン自身のディレクトリや `uploads` の `.htaccess` のみに依存しません。Apache・Nginx・静的配信の差異を避けるためです。私有ディレクトリは同一OSユーザーからの完全な隔離を提供しないため、ホスティングのアカウント分離も必要です。

## 将来のサービス分離

販売サーバーは顧客アカウント、Stripe同期、ライセンス、更新署名・配信を担当する別のサービスとします。購入者のWordPressへStripe秘密鍵や署名用秘密鍵を配布しません。WordPress側には必要なライセンス認証情報と署名検証用公開鍵のみを保持します。

基本防御と商用サービスへの到達性を分離します。販売サーバー停止、契約照会失敗、Cloudflare API失敗によってローカルの既存防御を解除しません。不正な更新ZIPや署名不一致のルールは拒否し、最後に検証済みの状態を保持します。詳細は将来API仕様を参照してください。

## 対応範囲と変更管理

PHP 8.2以上の型機能を利用し、現行サポート中の8.2〜8.5をCI対象とします。WordPressは7.0・7.1の最新パッチを対象候補とし、実行できた結果から正式な対応表を決定します。マルチサイト、非WordPressの独立PHPアプリへの組込は別工程です。

`1.0.0-dev` → `1.0.0-rc.1` → `1.0.0-rc.2` → `1.0.0` の順で昇格します。RC番号を作るだけでは品質ゲートを満たしません。CI・実機検証・セキュリティ監査・承認の結果をリリース単位で記録します。
